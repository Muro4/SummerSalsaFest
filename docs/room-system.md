# Room and roommate system audit

## Findings and implemented changes

| Original issue | Resolution |
| --- | --- |
| Lock API accepted any string starting with Bearer without verifying it | Firebase token verification and a server-side ambassador/superadmin role check |
| Temporary draft IDs and permanent occupants shared one array | Separate `locks` and `occupants`; shared normalization for legacy records |
| Sweeper read old snapshots and overwrote entire arrays in a batch | Paginated scan, then a fresh transaction per room; confirmed records never expire |
| Ticket creation wrote tickets without updating rooms | One transaction confirms every ticket and converts all its holds, or commits nothing |
| Draft could reserve multiple rooms, or release another owner's entry | Owner-scoped `room_drafts` document serializes moves, release, and confirmation |
| Double submission could issue duplicate tickets | Stable ticket document per owner/draft; finalized draft records and display-code reservations |
| Admin capacity/deletion/day edits used stale browser arrays | Superadmin API transacts against current room and ticket state |
| Global browser timer erased every attendee's selection | Each hold has its own server expiry; expired assignments stay visible and block confirmation |
| Deleting a draft did not unlock its room | Explicit bulk/single release completes before local removal; navigation sends a keepalive release |
| Room prices differed across ambassador/admin views | Draft totals and ticket accommodationPrice use room nightly price × nights |

## Contract and invariant

`databaseStructure.json` contains example records. It is documentation, not a production migration.

- `rooms/{id}`: schemaVersion 2, hotelId, roomNumber, roomType, integer capacity (1–20 for new/edited rooms), pricePerPersonPerNight, isBlocked, occupants[], locks[].
- `occupants[]`: permanent ticketId (Firestore document ID), ticketID (display code), name, gender, passType, ambassadorId/name, days. The legacy `id` alias is retained.
- `locks[]`: ownerId, draftId, name, optional gender, days, expiresAt (UTC epoch milliseconds).
- `room_drafts/{sha256(JSON.stringify([ownerId, draftId]))}`: held/released/finalized state, roomId, expiresAt; finalized records also hold ticketId. Draft IDs are unique per attendee, generated by the browser.
- Tickets store roomId, accommodation (hotelId or `None`), days, accommodationPrice and ambassador metadata. `price` remains the festival-pass price; accommodationPrice is separate. Staff-created tickets are active. Their optional attendee email is validated and saved as `guestEmail` for the existing ticket-delivery form; the ambassador remains the ticket owner.
- Rooms also store `board`: none, breakfast, halfBoard, fullBoard, or allInclusive. Older rooms without this field display None.
- `settings/hotel_financials` stores `{[hotelId]: {defaultRate, adjustments}}`; `settings/hotel_deposits` retains the existing `{[hotelId]: deposit}` contract. All values are EUR. Signed adjustments add fees or subtract discounts. Default rates pre-fill new rooms; each room keeps its own negotiated rate.
- `ticket_codes/{displayCode}` reserves six-character display IDs. `ticket_purchase_guards/{uid}_{year}` serializes the existing public purchase limit.

At every allocation write:

`confirmed occupants + holds whose expiresAt > server time <= capacity`

Expiry is evaluated inside each transaction attempt. Capacity does not depend on the sweeper or the cached status field. Moving between rooms reads and updates both rooms atomically; a full destination leaves the source unchanged. Admin capacity edits count active holds as well as confirmed occupants. Blocking prevents new allocations and draft confirmation, while existing occupants remain intact.

Firestore transactions follow the documented [read-before-write and retry semantics](https://firebase.google.com/docs/firestore/manage-data/transactions). There are no irreversible side effects inside transaction callbacks.

## API

All POST requests require a verified Firebase ID token.

- `POST /api/rooms/lock`: ambassadors/superadmins. `{action: "lock", roomId, draftId, name, gender}` acquires, moves, or explicitly renews a ten-minute hold. The `details` action updates the name/gender of an existing hold without extending its expiry. `{action: "unlock", draftId}` or `{action: "unlock", draftIds: [...]}` releases only that caller's temporary holds. Finalized drafts are immutable to unlock.
- `POST /api/tickets/create`: staff registration includes `isAmbassadorRegistration: true` and `tickets[{draftId, roomId, userName, passType, gender, accommodation}]`. Every assigned attendee must own an unexpired hold. A single invalid assignment rejects the whole group. Pass-only attendees send roomId null and accommodation None. Public purchase callers cannot book accommodation or select restricted pass types.
- `POST /api/rooms/manage`: superadmin only. Actions: create/update/block/delete, assign, evict, days, deposit. Reassignment and eviction update the ticket and room(s) together. `evictOrphan` can remove a legacy allocation only after checking no corresponding ticket exists.
- `GET /api/rooms/sweep`: `Authorization: Bearer <CRON_SECRET>` or a verified superadmin token. Reads rooms in pages of 100, re-reads each candidate inside a transaction, and removes only expired holds. Configure your scheduler to call this endpoint periodically.

Validation failures use 400, missing records 404, authentication/role failures 401/403, allocation conflicts 409. Error codes map to English and Bulgarian RoomSystem translations.

## UI and lifecycle

Ambassadors use a compact draft table with optional attendee email, pass, accommodation, commission and final-price columns. Choosing a hotel opens a room-selection modal. A successful assignment closes it and displays a room tag with the remaining hold time. Cancelling the modal preserves the previous assignment; moves still execute atomically. Attendee rows do not collect gender.

Admins see four permanent hotel sections (VFU/ВСУ, Detelina, Toro Negro and Kabakum), including hotels without rooms. Each section contains a dense table with one row per bed and shared cells for room number, board and room total. Room creation/editing, allocations and hotel financial settings use keyboard-accessible modals. Empty/held/confirmed beds remain distinguishable. Search and availability filters affect table rows, not hotel summaries.

Financial totals count confirmed stays only. Remaining = room totals + adjustments - deposit. EUR/BGN amounts use the [ECB's fixed conversion rate of 1.95583](https://www.ecb.europa.eu/press/pr/date/2025/html/ecb.pr250708~b9676a9fa8.en.html). Hotel financial settings are saved atomically through the superadmin `financials` action on /api/rooms/manage; existing room rates and holds are not modified.

The draft roster remains local; assigning a bed shares that attendee's name with authorized room staff. Closing a view or tab attempts an authenticated keepalive release; browsers cannot guarantee network delivery during abrupt termination. Server expiry always recovers those holds after ten minutes. Failed explicit releases retain the local draft and display an error. Returning to an expired/released assignment requires reselecting a bed.

## Legacy rollout and security requirements

1. Merge the rules in `room-security.rules` into the actual deployed Firestore rules. No deployed rules or Firebase deployment configuration were present in this repository, and this change does not deploy rules. Client writes to rooms, room_drafts, ticket_codes, and ticket_purchase_guards must be denied, including to admins. Prevent direct client edits to ticket allocation fields; privileged SDKs perform the validated transaction instead.
2. Remove overlapping broad allow rules. Firestore rules are additive: a specific `allow write: if false` does not override another matching allow. Prevent users from self-editing roles, since API roles are read from users/{uid}.
3. Before rollout, reconcile ambiguous old allocations against hotel records. Explicit legacy lockExpirations entries migrate as temporary holds; other old occupants are retained conservatively. New records with ticketId are always permanent. Old ticket creation never linked draft IDs to tickets, so missing links cannot be reliably inferred from existing data.
4. Release room allocations through the Rooms view before deleting tickets in the separate ticket-management screen. The rule guard below prevents deleting a ticket with a room. A historical orphan can be explicitly released after the API checks its ticket is absent. Ticket status changes (including the existing `used` check-in status) do not vacate a hotel bed.
5. Set CRON_SECRET in the server environment and configure the scheduler. Do not configure native Firestore TTL to delete room documents or finalized draft records. Keep finalized draft/code records for idempotency.

## Verification

`npm test` includes API transaction-race regression tests and rendered UI tests in both locales. The in-memory Firestore harness rejects reads after writes, validates document/query versions, and retries conflicting transactions. It exercises competing holds, moves, confirmation vs release/sweep, retries, expired locks, ownership, capacity changes and admin reassignments.

`npm run build` checks all application imports and production compilation. Real Firestore/emulator concurrency and deployed rules must also be verified in the deployment environment; the local Java runtime is Java 8 and no usable Firestore emulator was available during this change. No production data was mutated.
